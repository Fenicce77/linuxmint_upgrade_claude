Before you touch anything

Your session shows 8 logged-in users and 51 days of uptime — that's almost certainly stacked SSH/tmux/terminal sessions on one workstation, not 8 people. A mid-upgrade reboot kills all of them.

Check what else is running before you commit to a reboot window

tmux ls 2>/dev/null

# anything with uncommitted work — check running dev daemons
systemctl status docker mongod 2>/dev/null
Time budget This is not a 20-minute job. Between the jammy→noble jump and re-pointing ~15 third-party repos, block out a few uninterrupted hours and don't start it before something time-sensitive.
01

Flatten 21.3 first

You have 470 packages pending inside 21.3 itself. Never start a major version jump on top of a partially-updated system — resolve everything on the current base first, so mintupgrade is diffing against a known-good state.

sudo apt update
sudo apt full-upgrade -y
sudo apt autoremove -y
sudo reboot

After reboot, confirm you're clean:

apt list --upgradable 2>/dev/null | wc -l   # expect: 0 (or just the list header)
02

Snapshot and back up

The upgrade tool overwrites files under /etc with new defaults. A Timeshift snapshot is your undo button for both a broken boot and for hand-diffing config afterward — 201G free on / is plenty of room.

# if Timeshift isn't already set up
sudo apt install timeshift -y
sudo timeshift --create --comments "pre-mint22-upgrade" --tags D
Also back up separately Timeshift snapshots by default exclude /home. If you keep dev work, SSH keys, or DB dumps under your home directory, back those up independently (external drive, rsync, or cloud) — don't rely on the snapshot alone for anything you can't afford to lose.
03

Quarantine third-party repos

Your sources.list.d has 15 third-party entries. mintupgrade only understands Mint/Ubuntu sources — a stray jammy-pinned repo in the mix during the run can cause dependency resolution to fail or silently pull the wrong packages. Move them out of the way, run the upgrade against a clean base, then bring them back deliberately in Phase 6.

sudo mkdir -p /etc/apt/sources.list.d.disabled
sudo mv /etc/apt/sources.list.d/{antigravity,bazel,docker,mongodb-org-8.0,mwt-desktop,nodesource,percona-pbm-release,percona-psmdb-80-release,percona-telemetry-release,percona-tools-release,repo.fortinet.com,sublime-text}.list /etc/apt/sources.list.d.disabled/ 2>/dev/null
sudo mv /etc/apt/sources.list.d/{brave-browser-release,google-chrome,vscode}.sources /etc/apt/sources.list.d.disabled/ 2>/dev/null
# leave official-package-repositories.list — mintupgrade rewrites it itself
sudo apt update
04

Run mintupgrade

This is the official, supported tool for a major-version jump (21.3 → 22) — it is not the same mechanism as a point-release update, and plain apt dist-upgrade will not take you across the base change.

sudo apt install mintupgrade
sudo mintupgrade check    # dry run — read every warning it prints
sudo mintupgrade download
sudo mintupgrade upgrade
Known cosmetic bug Partway through, font rendering will break and text becomes unreadable in the terminal. This is expected and cosmetic — the tool is still working. Do not Ctrl-C, do not close the terminal, do not reboot until it reports completion.

Land on 22, reboot, check /etc

cat /etc/linuxmint/info   # expect RELEASE=22, CODENAME=wilma (or later point release)

Then diff your pre-upgrade snapshot against live /etc for anything the upgrade silently overwrote that you care about (custom fstab entries, SSH config, cron, sysctl tuning) — restore individual files from Timeshift as needed, don't restore the whole snapshot at this point.

07

Ride to 22.3

22 → 22.1 → 22.2 → 22.3 are point releases on the same Ubuntu base, but Mint deliberately doesn't let plain apt drive this jump — the package-source metadata differs per point release and the guidance is explicit not to hand-edit it. Use the GUI Update Manager.

In Update Manager

Refresh, then Edit → Upgrade to Linux Mint 22.x. It may only offer one point release at a time — run it, reboot, reopen Update Manager, repeat until it reports 22.3 Zena.

09

GPU & bootloader risk audit

Added after a deeper diagnostic pass on 2026-09-23. This machine isn't a plain desktop — it's a CUDA dev box running nvidia-driver-535 via DKMS with prime-select pinned to nvidia (pure discrete-GPU mode, no Intel fallback wired up). That combination concentrates most of the real risk in this upgrade.

Critical — NVIDIA DKMS rebuild with no iGPU fallback

The jammy→noble jump replaces the 5.15 kernel with a 6.8-series kernel. DKMS must rebuild the nvidia module against the new headers during the upgrade. Because Xorg is configured for nvidia-only (not Intel/NVIDIA offload), a failed rebuild means a black screen on first boot with nothing to fall back to — this laptop's Intel UHD 620 is present in hardware but not wired into the current X config.

# after `mintupgrade upgrade` finishes, before rebooting — confirm the module actually built
dkms status   # expect: nvidia/535.288.01, <new-kernel>: installed
# if it says installed-weak or is missing the new kernel line, fix it before rebooting:
sudo dkms install nvidia/535.288.01 -k $(ls /lib/modules | grep -v 5.15 | head -1)
Escape hatch if you already rebooted to a black screen Ctrl+Alt+F3 for a TTY → log in → sudo prime-select intel && sudo systemctl restart lightdm. That gets you a working Intel-only desktop so you can fix NVIDIA/DKMS from a GUI terminal instead of blind on a TTY.
Critical — grub-pc and grub-efi are both installed

This is an EFI/GPT system (boots via shimx64.efi) but grub-pc — the BIOS bootloader — is also installed, a leftover from the Mint installer covering both cases. Its postinst script can throw an interactive debconf prompt ("install GRUB to which drive?") mid-upgrade. If that fires during an unattended mintupgrade run, the terminal will look hung while it waits for input.

Mitigation Stay at the terminal for the mintupgrade upgrade step — don't walk away. If the grub-pc prompt appears, decline installing to any BIOS device (you don't need it). Optionally purge it ahead of time, since this system never boots via BIOS: sudo apt purge grub-pc grub-pc-bin.
Moderate — CUDA toolkit will jump versions

nvidia-cuda-toolkit on jammy is CUDA 11.5, plus the full Nsight Compute/Systems suite. Noble's repos ship a newer default CUDA branch. The upgrade won't fail because of this, but any environment, container, or script pinned to the CUDA 11.5 ABI will silently start pointing at a different toolkit version. Check before upgrading, not after:

pip list 2>/dev/null | grep -i cuda
grep -ril "cuda:11" ~/Dockerfile* ~/**/Dockerfile 2>/dev/null
conda env list 2>/dev/null
Moderate — systemd-oomd is new in Noble, not installed today

Ubuntu 24.04 enables systemd-oomd by default, which proactively kills processes under memory pressure. You run Docker, MongoDB, and Percona daemons on a 15G-RAM box that already runs close to its ceiling day to day — after the upgrade, check whether it's being trigger-happy with your dev services.

systemctl status systemd-oomd
systemd-cgtop   # watch memory pressure on docker.service / mongod.service under load
Low — stale package remnants

20 packages sit in rc state (removed, config retained), including three old kernel image/module sets and an orphaned linux-objects-nvidia-535-5.15.0-171-generic for a kernel that was never actually installed. Harmless, but purging it first keeps mintupgrade check's output readable so a real warning doesn't get lost in the noise.

sudo apt purge $(dpkg -l | awk '/^rc/{print $2}')
